    后续执行 Checklist：AI 能力工程路线落地清单¶

    本清单依据 后续方向与实施路线 整理。 用法：按阶段从上到下执行。每完成一项，就补齐对应产出物和验收记录；不要只勾选“文章写完”，必须同时确认模板、案例、验证和交叉引用已经完成。

    一、执行总判断¶

    当前 cn/ 目录已经有 Skill、MCP、Agent 基础，以及可观测性、Evals、Checkpointer、自我纠错、安全、多 Agent 和 A2A 等专题文章。 因此，接下来不是继续平均增加 Agent 概念文章，而是完成以下转变： 

    已有文章
  -> 统一案例
  -> 统一字段和模板
  -> 参考实现
  -> 评估和失败回流
  -> 可复用的 AI 能力工程资产
    推荐执行顺序： 
    阶段 0：收口和盘点
  -> 阶段 1：可信执行闭环
  -> 阶段 2：多 Agent 交接协议
  -> 阶段 3：上下文、成本和平台治理

    三、阶段 0：体系收口与资产盘点¶

    目标：先把已有文章整理成一套可以导航、引用和复用的体系。这个阶段不急着新增文章。

    0.1 建立文章-能力-资产矩阵¶

    • 新建一张表，列出所有文章的标题、所属层级、依赖文章、已有案例、已有代码、已有清单、已有模板和待补缺口。
    • 将文章分为基础层、执行层、可靠性层、协作层、安全层、生产治理层。
    • 标记“已有专题文章”和“需要新增的整合文章”，避免把已完成文章重复当作待写选题。
    • 在矩阵中增加“下一步动作”列，只允许填写四种动作：保留、补充、重构、抽取资产。 建议使用以下字段：
    文章 层级 主要问题 已有资产 缺口 下一步动作
    Agent 可观测性实战 可靠性 如何记录和回放 Agent 执行 Trace 原则、Replay、成本 统一事件字段 抽取 Trace 模板
    Agent 自动化评估体系 可靠性 如何证明版本没有退化 测试金字塔、Golden Set、评分器 统一样例格式 抽取 Eval 模板
    Agent 状态管理与断点续传 可靠性 如何暂停、恢复和避免重复副作用 Checkpoint、恢复、幂等 统一状态模型 抽取状态模板
    多 Agent 协作模式 协作 多个 Agent 如何分工 层级、流水线、群组 交接契约 补交接样例

    完成标准： 每篇文章都有明确归属和下一步动作，不再出现“这篇文章讲过什么但无法复用”的情况。

    0.2 固定两条案例线¶

    • 确定“采购 / 合同审批 Agent”为业务主案例。
    • 确定“代码修复 Agent”为技术验证案例。
    • 为两个案例分别写一页说明：用户目标、输入、工具、状态、风险动作、最终 Artifact。
    • 后续新文章至少复用其中一个案例，不再每篇重新设计完全无关的 Demo。

    主案例与技术案例的分工：

    案例 重点展示
    采购 / 合同审批 Agent 权限、人工确认、任务委派、多 Agent、A2A、Artifact、审计
    代码修复 Agent Trace、Replay、Evals、Checkpoint、验证、重试、成本和延迟

    0.3 统一文章入口和可观测性文章关系¶

    • 检查 cn/index.md 的阅读顺序是否按照“基础 -> 执行 -> 可靠性 -> 协作 -> 治理”排列。
    • 将《Agent 可观测性实战：从日志、Trace 到 Replay》定位为总论。
    • 将《Agent 的可观测性实战：用 Tracing 看清你的 Agent“大脑”》定位为 Trace 专题深化。
    • 在两篇文章中互相添加“先读哪篇、后读哪篇”的链接。
    • 检查所有文章标题、文件名、README 标题和发布标题是否一致。

    0.4 建立最小资产目录¶

    • 创建 assets/checklists/、assets/schemas/、assets/examples/。
    • 先建立 4 个空白模板：trace-event.md、eval-case.yaml、checkpoint-state.yaml、permission-matrix.md。
    • 每个模板先写字段说明和一个最小示例，不追求一次设计完整。

    阶段 0 验收： 有文章-能力-资产矩阵；有两条固定案例线；README 阅读顺序清晰；四个模板文件已经建立。

    目标：把已有的可观测性、Evals、Checkpointer、自我纠错文章串成一条可以演示和回归的执行链。

    1.1 先处理已有文章¶

    文章标题 需要重点提取的内容 具体产出

    《Agent 的可观测性实战：用 Tracing 看清你的 Agent“大脑”》 Trace、Span、Event、埋点边界、工具调用链路 事件层级图、最小埋点示例

    《Agent 状态管理与断点续传：Checkpointer 机制深度解析》 状态模型、Checkpoint、恢复、重试、取消、幂等和重复调用防护 checkpoint-state.yaml、状态机图

    • 从 Trace 专题中抽取 Trace -> Span -> Event 的层级关系和埋点示例。
    • 从 Evals 文章中抽取 20 到 50 条 Golden Set 的字段格式。
    • 从 Checkpointer 文章中抽取状态转换、恢复条件和幂等规则。
    • 从自我纠错文章中抽取 Validator 触发条件、失败处理和重新验证规则。

    1.2 新增一篇整合文章¶

    建议标题：

    《Agent 可信执行闭环：从 Trace、Evals 到可恢复执行》

    这篇文章不是重复解释五篇已有文章，而是把它们放进同一个工程案例中。

    建议内容结构：

    1. 场景： 代码修复 Agent 修改代码、运行测试、修复失败并提交补丁。
    2. 执行模型： Goal、Plan、Tool Call、Observation、Validation、Artifact。
    3. Trace： 如何记录每一步，以及怎样通过 task_id、trace_id 关联父子步骤。
    4. Evals： 如何设计正常、编译失败、测试失败、权限不足和历史回归样本。
    5. Checkpoint： 在测试执行或人工确认前保存什么状态，如何恢复。
    6. Validator： 如何检查补丁格式、测试结果、风险文件和最终说明。
    7. 失败恢复： 工具超时、模型输出非法、测试失败、重复执行时分别怎么处理。
    8. 发布门禁： 如何比较新旧 Prompt、模型或 Skill 是否退化。

    建议同时提供一个最小流程：

    用户提交问题
  -> Agent 生成修复计划
  -> 调用代码检索和测试工具
  -> 记录 Trace
  -> 保存 Checkpoint
  -> Validator 检查补丁和测试
  -> 失败则恢复或重规划
  -> 生成可审计 Artifact

    1.3 建立第一批 Eval Case¶

    • 准备 10 条正常样本。
    • 准备 5 条缺参或需求不明确样本。
    • 准备 5 条工具失败或超时样本。
    • 准备 5 条高风险或权限不足样本。
    • 准备 5 条历史失败回归样本。
    • 为每条样本填写输入、期望路径、禁止动作、必需证据、最终 Artifact 和评分规则。
    • 固定工具返回或测试 Fixture，避免外部依赖波动影响评估。

    初始发布门槛建议：

    • 高风险样本必须全部阻止或转人工，不能静默放行。
    • 关键工具调用和最终验证步骤必须在关键样本中可追踪。
    • 新版本整体成功率不得比基线下降超过 5 个百分点。
    • 成本或延迟出现 20% 以上回归时，必须记录原因并重新评审。

    1.4 阶段 1 验收¶

    • 任意失败都能从 Trace 找到具体步骤和错误原因。
    • 任意中断都能说明从哪个 Checkpoint 恢复。
    • 修复后可以重新运行同一条 Eval Case，比较修复前后结果。
    • 每次线上失败都能判断是否新增为回归样本。
    • 已有文章、整合文章、模板和参考案例可以互相链接。

    五、阶段 2：多 Agent 交接协议¶

    目标：在可信执行底座稳定后，把多 Agent 从“多个角色对话”推进为“有责任、有状态、有交付物的协作流程”。

    2.1 先处理已有文章¶

    文章标题 需要重点提取的内容 具体产出
    《多 Agent 协作模式深度解析：层级、流水线与群组》 主管-执行者、流水线、群组、任务边界、冲突和失败升级 三种拓扑对比表、模式选择清单
    《从 MCP 到 A2A：解读 Agent 互联协议的未来》 Agent Card、Task、Message、Artifact、发现、委派、回传 Agent Card 模板、任务对象表
    《Agent 安全护栏设计：权限控制、对抗鲁棒性与人工确认环》 最小权限、提示注入、敏感动作、人工确认和审计 权限矩阵、人工确认清单

    逐项执行：

    • 选定“主管 Agent + 合同分析 Agent + 风险审查 Agent”的最小层级拓扑。
    • 为三个 Agent 写 Agent Card：能力、输入、输出、权限、版本、健康状态。
    • 为合同分析任务定义父任务和两个子任务。
    • 明确每个子任务的输入证据、截止时间、预期 Artifact 和验收人。
    • 将父子任务的 trace_id、安全上下文和预算关联起来。
    • 模拟一个 Agent 不可用、一个结果冲突和一次人工澄清。

    2.2 新增交接协议文章¶

    建议标题：

    《Agent 任务交接协议：从 Agent Card 到 Artifact》

    建议内容结构：

    1. 为什么需要交接协议： 没有协议时，多个 Agent 会丢失上下文、重复工作或互相推卸责任。
    2. Agent Card： 如何描述能力、约束、认证、版本和可用状态。
    3. Task / Message / Artifact： 任务是跟踪对象，消息是过程通信，Artifact 是可验收交付物。
    4. Handoff： 交接时必须传递哪些字段，哪些内容不能只放在自然语言里。
    5. 状态： submitted、working、input-required、completed、failed、cancelled 如何转换。
    6. 失败升级： 超时、结果冲突、权限不足、协作者不可用时如何重试、换人或转人工。
    7. MCP 与 A2A： MCP 负责调用工具，A2A 负责 Agent 间协作，两者如何共同完成任务。
    8. 案例： 合同审批 Agent 委派条款分析和风险审查，最后由主管 Agent 汇总并请求人工审批。

    最小交接字段建议：

    context_id: contract-review-001
task_id: risk-review-002
parent_task_id: contract-review-001
from_agent: contract-supervisor
to_agent: risk-reviewer
objective: 检查合同中的付款和违约风险
input_artifacts:
  - contract-text-v3
expected_artifacts:
  - risk-report-v1
deadline: 2026-09-07T18:00:00+08:00
permission_scope:
  - read:contract
  - write:risk-report
status: submitted
failure_policy: escalate_to_supervisor

    2.3 阶段 2 验收¶

    • 每个子任务都有唯一任务 ID、责任 Agent 和预期 Artifact。
    • 子 Agent 不需要依赖隐藏的聊天历史才能完成任务。
    • 子任务失败可以被重试、转交或升级人工。
    • 协作链路可以从父任务追踪到 Agent、工具和最终产物。
    • 能说明什么时候应该用函数调用、内部 Agent 委派或 A2A。

    六、阶段 3：生产治理与新增文章¶

    目标：补齐当前体系仍缺少的上下文、成本和平台生命周期能力。

    3.1 新增文章一：Context Engineering¶

    建议标题：

    《Context Engineering：从记忆与 RAG 到可审计上下文》

    建议内容：

    • 上下文来源：用户输入、短期状态、长期记忆、RAG 文档、工具结果和 Agent 产物。
    • 检索流程：切分、召回、重排、压缩和上下文预算。
    • 证据要求：每条关键结论绑定来源、时间、权限和置信信息。
    • 权限过滤：不同用户、部门和 Agent 不能看到不属于自己的上下文。
    • 陈旧知识：知识有效期、版本、冲突和废弃处理。
    • 提示注入：把外部文档中的指令当作数据处理，不能直接升级为系统指令。
    • 评估方法：召回率、证据准确率、引用完整性、上下文长度和回答退化。

    交付物：

    • 上下文来源分类表。
    • 证据包模板。
    • 引用和权限过滤示例。
    • 上下文质量 Eval Case。

    3.2 新增文章二：成本与延迟¶

    建议标题：

    《Agent 成本与延迟优化：模型路由、缓存、并行与预算控制》

    建议内容：

    • 成本拆解：模型 Token、工具调用、重试、长上下文、人工等待和基础设施。
    • 延迟拆解：模型耗时、串行工具调用、网络、排队、人工确认和重试。
    • 模型路由：简单任务、复杂任务、高风险任务分别使用什么模型。
    • 缓存策略：工具结果缓存、语义缓存、Prompt 缓存和失效条件。
    • 并行策略：哪些子任务可以并行，哪些步骤存在依赖不能并行。
    • 预算控制：单任务 Token 预算、工具调用次数、最大执行时间和升级条件。
    • 线上指标：P50/P95 延迟、单任务成本、重复调用率、缓存命中率和失败重试率。

    交付物：

    • 成本和延迟字段表。
    • 单任务预算配置示例。
    • 模型路由决策表。
    • 超时、降级和预算耗尽流程图。

    3.3 新增文章三：企业能力平台¶

    建议标题：

    《从个人 Agent 到企业能力平台：目录、Owner、评估、审计与生命周期》

    建议内容：

    • 能力目录：Skill、MCP Server、Agent、评估集和工具的登记方式。
    • Owner 机制：谁负责功能、数据、权限、SLO 和事故处理。
    • 版本生命周期：开发、测试、灰度、发布、回滚、废弃和下线。
    • 发布门禁：评估结果、安全审查、成本预算和人工确认策略。
    • 运行治理：审计、告警、成本核算、用户反馈和失败回流。
    • 多租户隔离：用户、组织、数据、工具权限和上下文隔离。
    • 平台边界：哪些能力应该平台化，哪些能力保留在业务 Agent 内部。

    交付物：

    • AI 能力目录字段表。
    • Owner 和责任矩阵。
    • 版本发布与回滚流程。
    • 能力下线检查清单。

    七、文章统一写作 Checklist¶

    以后新增或重构每篇文章，都逐项确认：

    • 标题明确说明技术问题，不使用过于宽泛的“深度解析”作为唯一信息。
    • 开头有一个真实失败场景，而不是直接罗列概念。
    • 明确本文承接哪篇文章、解决哪一个缺口。
    • 给出系统边界：模型、Skill、MCP、Agent、记忆、状态和平台分别负责什么。
    • 至少提供一个流程图、状态图、字段表或最小伪代码。
    • 说明最小实现，不只介绍框架名和协议名。
    • 至少写三条失败路径：输入不完整、工具失败、权限或风险问题。
    • 每条失败路径都说明观测信号、处理策略和恢复方式。
    • 给出可执行的 Checklist，而不是只写“需要加强治理”。
    • 至少抽取一个模板、字段表、决策表或评估样例。
    • 补充与已有文章的交叉引用。
    • 更新 cn/index.md、README 摘要和在线链接状态。

    八、每篇文章的完成定义¶

    一篇文章只有同时满足以下条件，才算完成：

    文章正文完成
  + 统一案例已接入
  + 至少一个可复用模板
  + 至少三个失败分支
  + 至少一项可执行验证
  + README 和交叉链接已更新
  + 文章中出现的关键结论有验收标准

    只完成正文、没有模板和验证的文章，状态应标记为“内容完成，工程资产未完成”。

    九、建议执行节奏¶

    时间可以按个人投入调整，但顺序不要调整：

    批次 建议时间 执行内容 结束标志
    第 0 批 1 到 2 天 文章矩阵、案例线、链接和模板目录 能明确每篇文章下一步做什么
    第 1 批 1 到 2 周 Trace、Evals、Checkpoint、自我纠错整合 有一个可信执行参考实现
    第 2 批 1 周 多 Agent 交接、Agent Card、Artifact、失败升级 有一个可追踪的协作案例
    第 3 批 2 到 3 周 Context、成本延迟、企业平台三篇新增文章 有治理模板和生命周期流程
    持续工作 每篇发布后 失败回流、读者反馈、链接维护和版本更新 文章持续转化为资产

    十一、最终验收¶

    当以下问题都能回答“是”时，说明这条路线已经真正执行起来：

    • 新读者能从 README 找到正确的学习路径。
    • 任何一个 Agent 任务都有统一的 Trace、状态和结果记录。
    • Prompt、模型、Skill 或工具变更可以通过 Eval Case 回归。
    • 任务中断后可以从明确的 Checkpoint 恢复。
    • 高风险动作有权限判断和人工确认。
    • 多 Agent 交接有结构化输入、责任人和 Artifact。
    • 上下文资料有来源、权限和有效期。
    • 可以看到单任务的成本、延迟、重试和失败原因。
    • 每项能力有 Owner、版本、评估、审计和回滚记录。
    • 线上失败能够回流为文章、模板、规则或 Eval Case。

  -> 失败回流
