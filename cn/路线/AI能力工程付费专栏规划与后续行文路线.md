# AI 能力工程付费专栏规划与后续行文路线

> 本文基于 [后续方向与实施路线](后续方向与实施路线.md)、[后续执行 Checklist](后续执行Checklist：AI能力工程路线落地清单.md) 和 `cn/` 目录现有文章整理。
> 目标是把已有的 AI 能力工程知识体系，转化为一套读者愿意付费、能够跟着完成、并且可以持续更新的工程专栏。

## 一、先确定收费模式的基本判断

开始收费后，后续行文的评价标准会发生变化。

免费文章主要解决：

- 读者是否理解 Skill、MCP、Agent 的基本概念。
- 读者是否认可作者的工程判断。
- 读者是否愿意继续关注这个主题。

付费专栏必须进一步解决：

- 读者能否按照文章完成一个真实 Agent 项目。
- 读者能否拿到可复用的模板、代码结构、评估样例和检查清单。
- 读者能否定位失败、恢复任务并验证版本是否退化。
- 读者是否能把 Demo 推进到安全、可观测、可治理的生产形态。

因此，收费后不能只是把已有文章设置为付费，也不能只是增加文章数量。付费价值应该来自：

```text
公开知识
  -> 统一案例
  -> 分步实现
  -> 可复用资产
  -> 评估和验收
  -> 持续更新与答疑
```

一句话定位：

> 免费内容负责建立认知和信任，付费专栏负责交付一套可以照着完成的 AI 能力工程实践路径。

## 二、推荐的产品定位

### 2.1 建议的专栏名称

推荐标题：

> **《AI 能力工程实战：从 Skill、MCP 到可治理 Agent》**

副标题：

> 以统一案例为主线，构建可观测、可评估、可恢复、可协作、可治理的 Agent 系统。

也可以使用更强调结果的标题：

> **《生产级 Agent 工程：从最小闭环到能力平台》**

第一种标题更适合承接现有 `Skill -> MCP -> Agent` 系列；第二种标题更适合吸引已经做过 Demo、正在遇到工程问题的开发者和技术负责人。

### 2.2 建议的目标读者

专栏不建议同时服务所有人。第一版建议锁定以下三类读者：

| 读者 | 主要问题 | 付费原因 |
| :--- | :--- | :--- |
| Agent 开发者 | Agent 能跑，但无法稳定评估、排障和恢复 | 想获得可运行的工程方法和模板 |
| 平台 / 后端工程师 | 需要把模型、工具、权限、日志和评估接成平台 | 想减少架构摸索和重复试错 |
| 技术负责人 | 关心成本、安全、上线门槛和长期维护 | 想得到可评审、可治理的落地框架 |

不建议把专栏定位成“零基础 AI 入门”。基础概念可以继续通过公开文章覆盖，付费内容应默认读者已经了解 Python、API、LLM 和基本 Agent 概念。

### 2.3 推荐的收费形态

建议第一版采用：

> **一次性购买专栏 + 持续更新内容和资产。**

原因是当前内容更接近一套结构化课程和工程资料库，而不是每天必须消费的社区服务。只有在同时提供固定频率答疑、代码托管、作业批改、社群和版本服务时，才适合进一步做订阅制。

建议分三个阶段：

| 阶段 | 内容 | 收费策略 |
| :--- | :--- | :--- |
| 预热期 | 公开目录、公开样章、部分模板和案例说明 | 免费，用于验证选题和读者需求 |
| 首发期 | 先交付可信执行主线和第一批模板 | 早鸟 / 共创价格，明确后续更新范围 |
| 完整期 | 完成协作、治理、平台和全部资产 | 正式价格，持续补充修订和案例 |

不要在目录和交付边界还没有稳定时急于承诺“永久更新”或无限答疑。应明确更新范围、更新频率和答疑边界。

## 三、免费内容与付费内容的边界

现有 `cn/` 文章适合继续作为公开认知层，不建议全部隐藏。公开内容越清晰，付费专栏越容易建立信任。

| 内容层 | 免费公开 | 付费专栏 |
| :--- | :--- | :--- |
| 概念 | Skill、MCP、Agent 的定义、关系和基本原理 | 把概念组合成完整系统的架构判断 |
| 方法 | 规划、记忆、工具调用、基础安全原则 | 可直接执行的流程、字段、决策表和验收门槛 |
| 案例 | 简化案例、局部代码、问题分析 | 一个主案例的完整实现、失败路径和版本演进 |
| 可靠性 | 可观测性、Evals、Checkpoint 的知识介绍 | Trace Schema、Eval 数据集、恢复流程和回归门禁 |
| 协作 | 多 Agent、A2A 的概念和协议介绍 | Agent Card、Handoff、Artifact 和冲突仲裁样例 |
| 治理 | 权限、安全和人工确认原则 | 权限矩阵、审计字段、发布流程、回滚和平台生命周期 |
| 资产 | 少量示例 | 完整模板库、样例代码、评估样本和版本记录 |

核心原则：

> 不收费的是“知道这件事”，收费的是“能把这件事做出来，并且知道如何验收和维护”。

## 四、专栏主线与统一案例

建议使用“一主一辅”的案例策略：

### 主案例：采购 / 合同审批 Agent

主案例适合支撑付费专栏，因为它同时包含业务价值和工程复杂度：

- 读取合同和采购资料。
- 调用规则、供应商、历史合同等 MCP 工具。
- 分析付款、交付、违约和合规风险。
- 委派给条款分析 Agent 和风险审查 Agent。
- 高风险结论进入人工确认。
- 生成风险报告、审批建议和可审计 Artifact。

### 辅助案例：代码修复 Agent

辅助案例用于讲清技术闭环：

- 读取代码和 Issue。
- 制定修改计划。
- 调用代码检索、编辑和测试工具。
- 记录 Trace。
- 在测试失败后恢复和重规划。
- 通过 Eval Case 比较不同版本。

主案例负责解释权限、协作、业务风险和平台治理；辅助案例负责解释 Trace、Evals、Checkpoint、验证、成本和延迟。两个案例不需要都做成完整产品，但必须共享同一套术语和模板。

## 五、付费专栏建议目录

第一版建议控制在 10 到 12 篇核心文章，避免专栏变成没有交付终点的文章集合。

### 第 0 篇：专栏导读与工程基线

建议标题：

> 《为什么 Agent Demo 能跑，生产系统却不稳定》

大致内容：

- 从一个“合同审批 Agent 能回答但不能上线”的失败案例切入。
- 解释模型、Skill、MCP、Agent、状态、评估和治理的分工。
- 介绍主案例、辅助案例、目录结构和最终交付物。
- 给出专栏学习顺序和环境准备方式。

交付物：

- 专栏知识地图。
- 项目目录说明。
- 主案例需求说明。
- 学习和验收清单。

这一篇可以作为公开样章，用于让读者判断是否适合购买完整专栏。

### 第 1 篇：从任务到执行模型

建议标题：

> 《Agent 统一执行模型：从 Goal、Plan 到 Artifact》

大致内容：

- 把用户目标、任务计划、工具调用、观察结果、验证和最终产物统一起来。
- 解释 Skill、MCP 和 Agent 在一次任务中的责任边界。
- 定义任务状态、工具调用和最终 Artifact。
- 给出采购审批和代码修复两个案例的执行流程。

交付物：

- Agent 执行流程图。
- 任务状态字段表。
- Artifact 定义模板。
- 一个最小 Agent 伪代码或流程实现。

### 第 2 篇：可观测性与 Trace

建议标题：

> 《Agent 可观测性实战：从 Trace 到 Replay》

大致内容：

- 在已有《Agent 可观测性实战：从日志、Trace 到 Replay》和 Tracing 专题的基础上，提供统一实现。
- 定义 `task_id`、`trace_id`、`span_id`、`event_type`、`tool_name`、`input_ref`、`output_ref`、`validation_result` 和 `cost`。
- 说明 Trace、Span、Event 的层级关系。
- 演示如何定位错误工具、错误计划、重复调用和成本异常。
- 说明哪些数据原文保存、哪些数据只保存摘要或引用。

交付物：

- `trace-event.md`。
- 一份真实任务 Trace 样例。
- 一张失败排障流程图。
- 一个 Replay 样例。

### 第 3 篇：自动化评估体系

建议标题：

> 《Agent Evals 实战：从 Golden Set 到发布门禁》

大致内容：

- 从“最终答案看起来正确”转向“任务过程和结果都可评估”。
- 设计正常、缺参、边界、工具失败、高风险、攻击和历史回归样本。
- 建立规则测试、工具契约、单步骤、轨迹、集成和线上回放六层评估。
- 讲清 Rubric、LLM-as-Judge、人工复核和失败归因。
- 把 Eval 接入 Prompt、模型、Skill 和工具变更流程。

交付物：

- `eval-case.yaml`。
- 第一批 20 到 50 条 Golden Set。
- 评分器和评估报告样例。
- 发布门禁清单。

### 第 4 篇：状态与可恢复执行

建议标题：

> 《Agent 可恢复执行：Checkpoint、幂等与失败重试》

大致内容：

- 定义 `pending`、`running`、`awaiting_confirmation`、`succeeded`、`failed`、`cancelled` 状态。
- 说明哪些状态必须持久化，哪些数据可以重新计算。
- 处理工具超时、模型失败、用户取消、人工等待和服务重启。
- 设计幂等键，避免恢复后重复付款、重复审批或重复写入。
- 对比重试、重规划、降级和人工升级。

交付物：

- `checkpoint-state.yaml`。
- 状态机图。
- 恢复策略表。
- 重复副作用防护清单。

### 第 5 篇：验证与自我纠错

建议标题：

> 《Agent 自我纠错工程：Validator、事实核查与 Reflection》

大致内容：

- 区分“让模型再想一遍”和真正的工程纠错。
- 设计输入校验、工具参数校验、结果校验、事实核查和最终产物校验。
- 说明什么时候重试、什么时候重规划、什么时候停止并转人工。
- 将纠错结果回流到 Memory、Skill、Eval 或权限规则。
- 把 Validator 失败写入 Trace，并形成回归样例。

交付物：

- Validator 决策表。
- 失败分类表。
- 纠错和升级流程图。
- 一个“失败 -> 修复 -> 再验证”的完整案例。

### 第 6 篇：可信执行闭环整合

建议标题：

> 《Agent 可信执行闭环：从 Trace、Evals 到可恢复执行》

大致内容：

- 将前五篇组合成一个完整的代码修复 Agent。
- 展示一次任务从计划、工具调用、验证、Checkpoint 到最终 Artifact 的全过程。
- 制造工具超时、测试失败、权限不足和错误计划四类故障。
- 演示如何通过 Trace 定位、通过 Checkpoint 恢复、通过 Validator 纠错、通过 Eval 验收。
- 给出从本地 Demo 到灰度发布的最小门槛。

交付物：

- 一个最小参考实现。
- 一组可回放失败样本。
- 一份发布前评估报告。
- 可信执行总 Checklist。

这篇是专栏最重要的交付节点，前面几篇提供零件，这一篇负责证明零件可以组装成系统。

### 第 7 篇：多 Agent 任务交接

建议标题：

> 《Agent 任务交接协议：从 Agent Card 到 Artifact》

大致内容：

- 解释什么时候需要多 Agent，什么时候普通函数调用更合适。
- 设计主管 Agent、合同分析 Agent、风险审查 Agent 的协作流程。
- 定义 Agent Card、Task、Message、Artifact 和 Handoff。
- 传递 `context_id`、`task_id`、父任务、输入证据、权限范围、预算和截止时间。
- 处理子 Agent 不可用、结果冲突、超时、重复提交和人工澄清。
- 说明 MCP 负责能力接入，A2A 负责 Agent 间协作。

交付物：

- Agent Card 模板。
- `handoff-contract.yaml`。
- 主管-执行者最小案例。
- 协作失败升级清单。

### 第 8 篇：安全护栏与人工确认

建议标题：

> 《Agent 生产安全：权限、提示注入与人工确认环》

大致内容：

- 建立工具权限、数据权限和动作风险三级模型。
- 处理提示注入、不可信文档、工具返回污染和越权请求。
- 为付款、删除、对外发送、审批和高金额操作设置人工确认。
- 记录谁在什么时间批准了什么动作。
- 将安全失败纳入 Trace 和 Eval，而不是只写安全原则。

交付物：

- `permission-matrix.md`。
- 高风险动作清单。
- 人工确认字段模板。
- 提示注入和越权回归样例。

### 第 9 篇：Context Engineering

建议标题：

> 《Context Engineering：从记忆与 RAG 到可审计上下文》

大致内容：

- 统一用户输入、短期状态、长期记忆、RAG、工具结果和历史 Artifact。
- 讲清切分、召回、重排、压缩、引用和上下文预算。
- 给每个关键结论绑定来源、时间、权限和有效期。
- 处理陈旧知识、冲突知识和文档中的提示注入。
- 评估召回质量、证据完整性、上下文长度和回答退化。

交付物：

- 上下文证据包模板。
- 引用和权限过滤示例。
- 上下文质量 Eval Case。
- 记忆和 RAG 的选择决策表。

### 第 10 篇：成本与延迟优化

建议标题：

> 《Agent 成本与延迟优化：模型路由、缓存、并行与预算控制》

大致内容：

- 拆解模型、Token、工具、重试、人工等待和基础设施成本。
- 分析模型推理、串行工具调用、网络、排队和人工确认延迟。
- 设计模型路由、工具结果缓存、Prompt 缓存和语义缓存。
- 规定单任务 Token、工具调用次数、最长执行时间和预算上限。
- 用 P50/P95 延迟、单任务成本、缓存命中率和重复调用率做优化。

交付物：

- 成本与延迟字段表。
- 单任务预算配置。
- 模型路由决策表。
- 超时、降级和预算耗尽流程图。

### 第 11 篇：企业能力平台

建议标题：

> 《从个人 Agent 到企业能力平台：目录、Owner、评估、审计与生命周期》

大致内容：

- 建立 Skill、MCP Server、Agent、工具和评估集的能力目录。
- 定义 Owner、数据责任人、安全责任人和事故处理人。
- 设计开发、测试、灰度、发布、回滚、废弃和下线流程。
- 将 Evals、安全审查、成本预算和权限策略接入发布门禁。
- 讨论多租户隔离、审计、SLO、成本核算和能力复用。

交付物：

- AI 能力目录字段表。
- Owner 和责任矩阵。
- 发布与回滚流程。
- 能力下线 Checklist。

## 六、现有公开文章如何转化为付费价值

不要简单复制现有文章。每篇公开文章进入付费专栏时，都应增加一个“工程增强层”。

| 现有公开文章 | 公开部分保留 | 付费增强内容 |
| :--- | :--- | :--- |
| 《AI 能力工程：从 Skill、MCP 到 Agent》 | 总体知识地图和三层关系 | 专栏项目结构、实现顺序、案例架构和验收路线 |
| 《Agent 工程实践指南》 | 最小闭环和生产问题 | 参考实现、发布门禁、失败演练和工程任务 |
| 《Agent 可观测性实战》 | Trace、Replay 和排障原则 | 完整字段、样例数据、查询方式和案例复盘 |
| 《Agent 自动化评估体系》 | 测试金字塔和评估方法 | Golden Set、评分器、报告和 CI 门禁 |
| 《Agent 状态管理与断点续传》 | Checkpoint 和恢复原理 | 状态 Schema、幂等代码、故障注入和恢复演练 |
| 《多 Agent 协作模式》 | 三种协作拓扑 | Handoff 契约、Artifact、冲突仲裁和协作案例 |
| 《从 MCP 到 A2A》 | 协议关系和基本对象 | Agent Card、任务流、认证、追踪和失败升级 |
| 《Agent 安全护栏设计》 | 威胁和防护原则 | 权限矩阵、人工确认、审计事件和安全 Eval |

付费内容的每篇文章最好都有一个明确回答：

> 读者看完以后，究竟多拿到了什么文件、什么代码、什么判断能力，或者什么可验收结果？

## 七、每篇付费文章的固定交付格式

每篇文章统一采用以下结构，降低读者学习成本，也方便后续持续更新：

1. **本篇要解决的问题**：用真实失败场景说明为什么需要它。
2. **本篇在专栏中的位置**：说明前置文章、后续文章和依赖资产。
3. **概念和边界**：只讲完成实现所需的原理。
4. **统一案例实现**：围绕采购 / 合同审批或代码修复案例展开。
5. **最小代码、配置或伪代码**：让读者能够启动实践。
6. **故障演练**：至少演示输入不完整、工具失败或权限风险中的三类情况。
7. **验证方式**：给出 Trace、Eval、状态或安全验收标准。
8. **可复用资产**：提供模板、表格、配置或样例数据。
9. **课后执行项**：读者可以在自己的项目中完成的 3 到 5 个动作。
10. **与下一篇的连接**：说明完成本篇后下一步应该做什么。

每篇文章的交付物至少包括一项：

- 一个 Markdown 模板。
- 一个 YAML / JSON Schema 示例。
- 一个最小代码片段。
- 一组 Eval Case。
- 一张决策表或检查清单。
- 一个失败复盘案例。

## 八、发布节奏与专栏运营

### 8.1 首发节奏

推荐采用“每周一篇核心文章 + 每两篇补一次资产更新”的节奏：

| 周次 | 发布内容 | 目的 |
| :--- | :--- | :--- |
| 第 0 周 | 公开导读、目录、样章和案例说明 | 验证读者是否认可主题 |
| 第 1 周 | 统一执行模型 | 让读者进入主案例 |
| 第 2 周 | Trace 与 Replay | 建立可观测基础 |
| 第 3 周 | Evals | 建立可验证基础 |
| 第 4 周 | Checkpoint | 建立可恢复基础 |
| 第 5 周 | Validator 与自我纠错 | 建立纠错闭环 |
| 第 6 周 | 可信执行闭环整合 | 交付第一个完整里程碑 |
| 第 7 周 | 多 Agent 任务交接 | 扩展协作能力 |
| 第 8 周 | 安全护栏与人工确认 | 建立风险边界 |
| 第 9 周 | Context Engineering | 处理上下文和证据 |
| 第 10 周 | 成本与延迟 | 处理运营指标 |
| 第 11 周 | 企业能力平台 | 完成平台治理收束 |

如果无法保持每周更新，应减少承诺，改为每两周一篇。稳定交付比短期堆积文章更重要。

### 8.2 每次发布后的闭环

- [ ] 更新专栏目录和文章状态。
- [ ] 更新对应模板或代码资产。
- [ ] 收集读者卡住的步骤和重复问题。
- [ ] 将高频问题补进正文、FAQ 或下一篇文章。
- [ ] 将真实失败整理成 Eval Case 或反模式。
- [ ] 记录文章是否被收藏、引用、实践和复用。
- [ ] 标记模板和代码的版本，避免读者使用过期资产。

## 九、收费专栏的验收指标

不要只用阅读量判断收费专栏是否成功。建议按四类指标观察：

| 指标类别 | 关注问题 | 具体信号 |
| :--- | :--- | :--- |
| 购买意愿 | 读者是否愿意为结果付费 | 目录点击、样章阅读、购买转化、退款原因 |
| 交付价值 | 读者是否真正得到帮助 | 模板下载、案例完成、Eval 运行、问题反馈 |
| 内容质量 | 哪些文章最有用 | 收藏、引用、复用、读者主动提交的改进 |
| 持续运营 | 是否值得继续更新 | 更新后的活跃度、重复问题减少、资产版本使用情况 |

收费专栏最重要的信号不是“文章有没有被看完”，而是：

> 读者是否拿着模板和案例，完成了一个以前自己无法稳定完成的工程任务。

## 十、付费专栏执行 Checklist

### 产品定位

- [ ] 确定第一版目标读者，不同时服务零基础读者和平台负责人。

- [ ] 确定代码修复 Agent 为技术辅助案例。
- [ ] 完成 10 到 12 篇专栏目录。
- [ ] 为每篇文章写出问题、内容、案例、交付物和验收标准。
- [ ] 标记哪些内容公开，哪些内容属于付费增强层。

## 十一、建议的第一步

收费专栏不应从“马上写第一篇新文章”开始，而应先完成一个最小商品闭环：

1. 确定专栏标题、目标读者和结果承诺。
2. 发布一篇免费导读：《为什么 Agent Demo 能跑，生产系统却不稳定》。
3. 用代码修复 Agent 做一个 Trace、Checkpoint、Validator 和 Eval 的最小案例。
4. 整理 `trace-event.md`、`eval-case.yaml` 和 `checkpoint-state.yaml` 三个模板。
5. 发布《Agent 可信执行闭环：从 Trace、Evals 到可恢复执行》作为第一篇核心付费内容。
6. 根据读者是否能运行案例、提出什么问题，再决定后续文章的深度和节奏。

这样可以先验证“读者是否愿意为工程闭环付费”，再投入多 Agent、Context Engineering 和企业平台等后续内容。

最终的付费专栏不应该是一组被隐藏的文章，而应该是一套具备明确结果的工程交付：

```text
知识理解
  -> 项目启动
  -> 能力实现
  -> Trace 记录
  -> Eval 验收
  -> 失败恢复
  -> 安全治理
  -> 持续运营
```
