# 后续方向与实施路线

> 本文基于 `cn/` 目录现有文章和《后续行文.md》整理。
> 目标不是继续罗列选题，而是回答两个问题：这套知识体系下一步应该往哪里走，以及怎样把文章推进成可运行、可验证、可复用的工程资产。

## 一、先下结论

当前系列已经完成了第一轮知识版图建设，主线可以概括为：

```text
Skill：沉淀专家方法
    -> MCP：协议化外部能力
    -> Agent：组织目标、计划、工具、状态和验证
```

现有内容已经较完整地回答了：

1. Skill、MCP、Agent 分别是什么，以及三者如何衔接。
2. Agent 如何规划、拆解任务、管理记忆和调用工具。
3. Agent 如何进行可观测、评估、断点恢复、自我纠错。
4. 多 Agent 如何协作，以及 MCP 与 A2A 的分工。
5. 生产环境中的安全护栏、人工确认和基本治理问题。

因此，下一阶段不应继续平均增加“Agent 又能做什么”的概念文章，而应从“主题覆盖”切换到“系统闭环”：

```text
能设计
  -> 能运行
  -> 能观测
  -> 能评估
  -> 能恢复
  -> 能协作
  -> 能治理
  -> 能沉淀为可复用资产
```

一句话判断：

> 当前系列已经完成了“是什么、为什么、怎么设计”的主体建设，后续重点是把已有知识串成一套“可验证、可恢复、可协作、可治理”的 AI 能力工程方法。

## 三、后续三条主线

### 方向一：可信执行底座

这是最高优先级。一个 Agent 如果看不见执行过程、无法证明结果、失败后无法恢复，后面的多 Agent 和平台化都会放大问题。

现有文章已经覆盖了这条线的主要专题：

- 可观测性：看见 Goal、Plan、Tool Call、Observation、Validation、Cost。
- Evals：把成功标准、轨迹要求和风险边界变成可回归测试。
- Checkpointer：保存任务状态，支持暂停、重试、恢复和幂等执行。
- 自我纠错：用 Validator、事实核查和 Reflection 处理失败，而不是只让模型“再想一遍”。

后续重点是把四个专题合成一条最小闭环：

```text
任务进入
  -> 生成计划
  -> 调用工具
  -> 记录 Trace
  -> 校验结果
  -> 保存 Checkpoint
  -> 失败则恢复或纠错
  -> 重新验证
  -> 形成 Eval 样本
```

#### 具体实施

1. 先定义统一执行事件模型，至少包含 `task_id`、`trace_id`、`span_id`、目标、计划、工具调用、观察结果、验证结果、人工确认、Checkpoint、成本、错误和最终产物。
2. 选一个小型 Agent 做参考实现，先打通一条完整链路，不追求覆盖所有框架。
3. 建立 20 到 50 条高价值 Golden Set，覆盖正常、缺参、边界、工具失败、高风险、攻击和历史回归样本。
4. 采用分层评测：规则单测、工具契约、单步骤能力、轨迹评测、集成场景、线上回放。
5. 定义状态机和幂等规则，明确 `pending`、`running`、`awaiting_confirmation`、`succeeded`、`failed`、`cancelled` 等状态如何转换。
6. 将每次线上失败回流为 Eval Case，并记录失败属于计划、工具、上下文、验证、权限还是恢复策略。

#### 阶段产出

- `Trace` 事件字段说明和示例。
- Eval Case 模板、评分器示例和回归报告样例。
- Checkpoint 状态模型、恢复规则和幂等键说明。
- Validator / Reflection 的决策表。
- 一个可以展示“执行、失败、恢复、再验证”的最小参考案例。

### 方向二：协作网络底座

单 Agent 能力稳定之后，复杂度会从“一个 Agent 怎么思考”转移到“多个能力单元如何分工”。这条线的核心不是让多个 Agent 互相聊天，而是让任务、责任、状态和产物都能被管理。

现有内容已经给出了多 Agent 的三种基本拓扑和 A2A 的协议对象。后续要把它们从概念说明推进到可执行契约：

```text
发现协作者
  -> 委派任务
  -> 结构化交接
  -> 执行并回传 Artifact
  -> 验证结果
  -> 收敛或升级人工
```

#### 具体实施

1. 先从一个主管 Agent 加两个专业 Agent 的层级模式开始，避免一开始搭建复杂群组网络。
2. 为每个 Agent 定义 Agent Card，说明能力、输入、输出、约束、认证方式、版本和健康状态。
3. 定义最小交接协议，至少包含 `context_id`、`task_id`、目标、输入证据、预期产物、截止时间、权限范围、回传状态和失败原因。
4. 明确 Task、Message、Artifact 的边界：消息用于沟通，任务用于跟踪，Artifact 才是可验收的交付物。
5. 将父子任务的 Trace、权限和成本关联起来，保证一次协作可以从总任务追到具体 Agent 和具体工具。
6. 为超时、重复交接、结果冲突、能力不可用和人工介入设计升级路径，不让失败停留在“再问一次”。

#### 阶段产出

- Agent Card 模板。
- Handoff / Task / Artifact 契约模板。
- 主管-执行者、流水线、评审仲裁三种模式的对比案例。
- 协作失败升级和冲突仲裁清单。
- MCP 与 A2A 的边界图：MCP 管能力接入，A2A 管 Agent 间协作。

### 方向三：生产治理底座

当能力跨团队、跨任务、跨环境复用时，系统的主要风险不再只是“回答错了”，还包括越权、数据泄露、成本失控、版本漂移和责任不清。

这条线应围绕以下五个问题推进：

1. Agent 能访问什么，谁批准，谁负责。
2. 上下文中哪些信息可信，是否有来源、权限和有效期。
3. 哪些动作必须人工确认，哪些动作可以自动执行。
4. 一次任务消耗了多少模型、工具和时间，是否满足预算与 SLA。
5. 一个能力由谁维护，如何评估、发布、回滚和下线。

#### 具体实施

1. **安全护栏**：建立工具权限、数据权限、动作风险三级矩阵；对外发、删除、付款、审批等不可逆动作设置人工确认；对提示注入、越权请求和不可信工具结果设置隔离与验证。
2. **上下文治理**：把记忆和 RAG 统一为上下文工程，覆盖检索、重排、压缩、引用、权限过滤、陈旧知识处理和上下文预算。
3. **成本与延迟**：在 Trace 中记录模型、Token、工具耗时、重试、并行度和缓存命中；再基于数据做模型路由、缓存、超时、预算和降级。
4. **平台治理**：建立能力目录、Owner、版本、评估结果、权限策略、审计记录、SLO 和下线流程，形成能力的完整生命周期。

#### 阶段产出

- 工具与数据权限矩阵。
- 高风险操作人工确认清单。
- 上下文证据包和引用模板。
- 成本、延迟和预算看板字段定义。
- AI 能力目录、版本发布和回滚流程。

## 四、统一实施方法：从文章到工程资产

后续每篇文章都应同时承担“解释知识”和“生产资产”两项任务。建议固定经过以下六步。

### 第一步：统一案例

建议采用“一主一辅”的案例策略：

| 案例 | 定位 | 覆盖主题 |
| :--- | :--- | :--- |
| 采购 / 合同审批 Agent | 主案例，体现业务风险和协作边界 | 任务拆解、MCP、权限、安全、人工确认、多 Agent、A2A、Artifact |
| 代码修复 Agent | 技术案例，便于观察执行轨迹和回归结果 | Trace、Replay、Evals、Checkpoint、验证、成本和失败恢复 |

主案例负责讲治理和协作，技术案例负责讲执行和验证。后续新增文章不应每次重新创造一个完全无关的场景。

### 第二步：固定文章结构

每篇文章至少回答以下问题：

1. 真实场景中的失败是什么。
2. 失败发生在哪个层：模型、上下文、工具、状态、权限还是协作。
3. 最小可行的结构、流程或代码怎么写。
4. 怎样观测、评估和验证它。
5. 失败后如何恢复、降级或升级人工。
6. 哪些内容可以抽成模板、清单或样例。

推荐的文章骨架是：

```text
场景与失败
  -> 第一性原理
  -> 系统结构与边界
  -> 最小实现
  -> 失败分支与排障
  -> 检查清单
  -> 与已有文章的关系
  -> 可复用资产
```

### 第三步：建立统一资产目录

可以先按下面的逻辑组织资产，目录名可根据实际仓库结构调整：

```text
assets/
  checklists/
    skill-design.md
    agent-release.md
    security-review.md
  schemas/
    trace-event.md
    eval-case.yaml
    handoff-contract.yaml
    checkpoint-state.yaml
  examples/
    code-repair-agent/
    procurement-agent/
  anti-patterns.md
  knowledge-map.md
```

首批不需要做成完整平台，优先抽取四类最有复用价值的资产：

- 检查清单：让读者可以按步骤自查。
- Trace / 状态 / 交接模板：让不同文章使用同一套字段。
- Eval 样例：让“效果好”变成可重复的判断。
- 权限矩阵：让高风险动作有明确边界。

### 第四步：建立最小验证门槛

每个主题至少要有一项可执行验证：

| 主题 | 最小验证 |
| :--- | :--- |
| Skill | 给定输入是否按约定步骤产出结构化结果 |
| MCP | Tool schema、错误码、权限和超时是否符合契约 |
| Agent | 计划、工具调用、验证和最终产物是否可追踪 |
| Evals | Golden Set 是否可重复运行，版本变化是否可比较 |
| Checkpoint | 中断后能否从正确节点恢复，是否避免重复副作用 |
| 安全 | 越权、注入、高风险动作是否被阻止或转人工 |
| 多 Agent | 交接是否结构化，结果是否有责任人和可验收 Artifact |
| 平台 | 能力是否有 Owner、版本、权限、指标和回滚路径 |

### 第五步：把失败变成资产

后续文章不能只展示成功路径。每个参考案例至少补三类失败：

- 输入不完整或意图不明确。
- 工具超时、返回异常或结果不可信。
- 权限不足、需要人工确认或执行不可逆动作。

每次失败都要记录四件事：触发条件、可观测信号、处理策略、是否新增回归样例。这样文章才能不断反哺 Evals、Validator、Skill 和治理规则。

### 第六步：完成文档收口和反馈闭环

一篇文章完成后，固定检查：

1. 文件名、标题、README、原文链接是否一致。
2. 本地链接是否可用，在线发布状态是否明确。
3. 是否补齐承接文章、后续文章和交叉引用。
4. 是否包含场景、最小实现、失败分支、清单和模板。
5. 发布后的评论、收藏、引用和“有没有代码/模板”的问题，是否回流到下一轮修订。

文章只是知识资产的第一层形态，最终要沉淀成“文章 + 案例 + 模板 + 样例 + 评估数据”的组合。

## 五、分阶段实施路线

### 阶段 0：体系收口与资产盘点

**目标：** 先把已有内容整理成可导航、可引用、可复用的体系。

**实施事项：**

1. 以 `cn/index.md` 为入口，按基础、执行、可靠性、协作、安全、生产治理重新检查阅读顺序。
2. 明确两篇可观测性文章的总论与专题关系，补齐互相引用。
3. 建立文章-能力-资产矩阵，标出每篇文章已有的案例、代码、清单、模板和缺口。
4. 统一核心术语：`trace_id`、`task_id`、`checkpoint`、`artifact`、`validator`、`human-in-the-loop` 等。
5. 确定采购 / 合同审批 Agent 和代码修复 Agent 两条案例线。

**验收结果：** 新读者可以从 README 找到适合的入口；维护者可以知道每个主题已有内容和下一步缺口；同一个概念在不同文章中不再使用多套名称。

### 阶段 1：可信执行参考实现

**目标：** 将可观测性、Evals、状态恢复和自我纠错串成一条可以演示的闭环。

**实施顺序：**

```text
Trace 数据结构
  -> Golden Set 与 Evals
  -> Checkpoint 与幂等恢复
  -> Validator / Reflection
  -> 失败回流与回归门禁
```

**实施事项：**

1. 为技术案例定义统一的任务轨迹表。
2. 为关键步骤增加结构化事件，而不是只增加文本日志。
3. 固定工具返回和外部依赖，先建立稳定的评测 fixture。
4. 让历史失败可以被回放、评分和比较。
5. 规定上线前的最低门槛：关键任务完成率、风险动作拦截率、人工升级准确率、重复调用率、成本和延迟。

**验收结果：** 任意一次失败都能回答“发生了什么、错在哪里、能否恢复、修复后是否退化”；模型、Prompt、Skill 或工具变更都可以重新运行同一组评估。

### 阶段 2：协作协议与交接样板

**目标：** 在可信执行基础上，把多 Agent 协作变成有边界、有责任、有产物的流程。

**实施事项：**

1. 先实现主管-执行者模式，再对比流水线和群组模式。
2. 为 Agent Card、任务委派、消息、Artifact 和人工升级定义最小模板。
3. 让子任务继承父任务的 `trace_id`、安全上下文和预算边界。
4. 模拟协作者不可用、结果冲突、任务超时、重复提交和人工澄清等失败路径。
5. 对比“普通函数调用、内部 Agent 委派、A2A 跨 Agent 调用”的适用边界，不把 A2A 当成默认答案。

**验收结果：** 每个子任务都有明确输入、责任 Agent、预期 Artifact、状态和失败处理；协作链路能够被追踪、评估和审计。

### 阶段 3：生产治理与平台化

**目标：** 把单个参考案例推进成一组可以长期运营的 AI 能力。

**实施事项：**

1. 建立权限矩阵、风险分级和人工确认规则。
2. 把记忆、RAG 和上下文压缩纳入统一的 Context Engineering 章节和模板。
3. 在 Trace 和 Evals 中纳入成本、延迟、SLA、预算和模型路由指标。
4. 建立能力目录、Owner、版本、评估记录、审计记录和回滚策略。
5. 最后再总结个人 Agent 到企业能力平台的迁移路径。

**验收结果：** 一个能力从设计、开发、评估、发布、运行、审计到下线都有责任边界和操作记录；新增能力可以复用既有模板和门禁，而不是重新从零开始。

## 六、后续写作与实施优先级

建议按“先整合已有内容，再补真正缺口”的顺序推进：

### P0：必须先完成

- 可信执行参考实现：把可观测性、Evals、Checkpointer、自我纠错串起来。
- 统一 Trace、Eval、状态和交接术语及字段。
- 抽取检查清单、评估样例、权限矩阵和失败样例。
- 更新 README 和知识地图，消除重复入口和断链。

### P1：接着完成

- Context Engineering：从记忆和 RAG 走向可审计上下文。
- 多 Agent 交接协议：把已有多 Agent、A2A 文章转成可复用模板。
- 统一案例的端到端示例：至少覆盖一次委派、人工确认、失败恢复和产物回传。

### P2：规模化后完成

- Agent 成本与延迟优化：模型路由、缓存、并行、超时和预算。
- 企业能力平台：能力目录、Owner、版本生命周期、审计、SLO 和成本核算。
- 课程化、示例仓库化或开源模板化，把文章体系转成可运行的学习和实践入口。

这里的优先级是工程依赖关系，不是单纯的发表顺序。某篇文章即使已经写完，只要还没有进入统一案例、模板或评估链路，就仍然没有完成它在知识体系中的第二阶段价值。

## 七、明确暂时不做什么

为了避免路线再次发散，近期应暂时避免：

1. 在已有基础概念已经足够的情况下，继续重复解释“Agent 是什么”。
2. 没有统一 Trace、评估和权限边界时，直接扩展复杂的多 Agent 网络。
3. 只增加框架或厂商名词，却不给出选择标准、失败模式和验证方法。
4. 为每篇文章重新设计一个互不相干的案例，导致知识无法积累。
5. 在没有模板、样例和验收指标的情况下，把“企业平台化”写成宏观口号。

后续所有新选题都应先通过一个判断：

> 它是在补一个真实工程缺口，还是只是在增加一个新名词？

## 八、最终路线图

```text
阶段 0：收口
文章索引 / 术语 / 案例 / 资产盘点
        |
        v
阶段 1：可信执行
Trace -> Evals -> Checkpoint -> Validator -> 回归门禁
        |
        v
阶段 2：协作网络
Agent Card -> 委派 -> Handoff -> Artifact -> A2A -> 冲突仲裁
        |
        v
阶段 3：生产治理
权限 -> 上下文 -> 成本延迟 -> 能力目录 -> 版本与审计
        |
        v
最终形态：文章、案例、模板、评估数据和示例代码共同组成 AI 能力工程资产库
```

最终要形成的不是一串孤立文章，而是一条可持续运行的知识生产线：

```text
真实失败
  -> 文章分析
  -> 模板和规则
  -> 参考实现
  -> Trace 与 Evals 验证
  -> 失败回流
  -> 能力持续演进
```

这就是后续最值得投入的方向：让 Skill、MCP、Agent 不只是知识体系中的三个关键词，而是能够被设计、运行、证明、协作和治理的一套完整工程方法。
